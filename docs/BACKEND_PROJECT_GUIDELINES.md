# Architecture for Backend

The application will strictly follow Hexagonal Architecture (also known as Ports and Adapters) to ensure a clear separation of concerns and maintain a framework-independent core.

- Framework-independent core (framework-agnostic): The domain and application layers will contain pure logic focused on business. No classes in these layers should depend on NestJS exception classes, as they are typically written for a specific type of application and would therefore make it difficult to reuse business rules and communicate domain-related problems.
- Dependency Injection via custom providers: The NestJS module system will be used exclusively as a binding layer. We will use custom providers to build and inject framework-independent services, repositories, and adapters into the application. All of this will be centralized in NestJS modules.
  - We will usually use `useFactory` providers at the 'infrastructure' layer as we need to define a adpater for ports
  - We will use `useExisting` providers when registering that a port must be bound to an existing adapter that is imported from some other module
  - For controllers, we must register as usual
  - For use cases provider classes, we will register as usual
- Adapters for external interactions: All interactions with external systems (databases, caches, third-party APIs, file system, etc.) must be encapsulated within adapters. These adapters will implement abstract interfaces (ports) defined in the application or domain layers. This ensures that the core logic depends on abstractions, not concrete external implementations, making the system more testable and maintainable.

Rules for domain entities or aggregate roots:

- Entities must be completely pure and deterministic. They cannot call Http, DB, or services that depend on infrastructure.
- Entities do not inject Domain Services. This would be circular coupling and would violate the "pure domain" principle.
- They are the only objects persisted directly by repositories.
- If an entity needs external data to validate an invariant, this validation must be done before instantiating the entity, through:
  - Domain Service (business decision),
  - Factory / Named Constructor (controlled creation).

## Domain services vs Application services

- Domain services represent pure business rules that do not naturally belong to a single entity.
- They orchestrate business actions — coordinating entities, other domain services, and repositories to execute a use case.

## About Application on Domain Ports

Regarding port placement:

- A port should be in the **domain** layer only when it represents an essential dependency of the business rule. That is, the domain only knows entities and invariants.
- If the port is necessary to execute one or more **use cases but is not part of the domain logic** itself, it belongs to the **application** layer. That is, the use case knows the flows and external dependencies.

To determine whether a new domain-related provider is a 'port' or not, ask yourself: "Does this describe the business rule? Or does it describe how technology supports fulfilling that rule?":

- If it's a 'Business rule' → treat it as a _Domain Service_
- If it's 'Technology required to carry out the rule' → treat it as a _Domain Port_

## Dependency Rules

Must respect the following layer dependency rules:

- ✅ Use case depends on Domain Services
- ✅ Use case depends on generic Application Services (e.g.: DateTime, Logger, Telemetry)
- ✅ Use case depends on Repositories (via ports)

Must avoid as it will violates the isolation on aggregate roots:

- ❌ Domain repositories calling other repositories
- ❌ Entities accessing repositories
- ❌ Circular dependencies between aggregates
- ❌ Domain/Application layers relying on the presentation layer (e.g.: references to DTO classes; references to HTTP-exceptions such as `BadRequestException`)

✅ Rule of thumb: The composition of data from multiple aggregates is never the responsibility of a repository — it is the responsibility of a service (application, domain, or infrastructure).

Should be avoided but can be tolerated in exceptional cases:

- Use case depends on Use case

Should always be avoided:

- ❌ Use case depending on Presentation (Controller, DTOs, CLI, etc)
- ❌ Use case depending on Infra (DB, HTTP client, etc)
- ❌ Domain depending on Infra without being via ports
- ❌ Domain importing Infra models (e.g.: a domain entity `domain/entities/{}.entity.ts` referencing a field from a DB schema model - file `{}.db.ts`)

Exceptional case:

- Scenario where the domain needs to know attributes from the persistence layer to enable query optimization in the persistence layer.  
  For example, when an entity has an `id` field generated by the DB instead of generated by the application

```ts
/** All the properties necessary to compose a new instance of the entity. */

    this.updatedAt = props.updatedAt;
    this.emailAddress = props.emailAddress;
  }

  static makeNew(props: Omit<IUserProps, "uuid" | "id">): IUnpersistedUser {
    const dummy = new User({
      ...props,
      id: 0n,
    });
    const user: IUnpersistedUser = Object.assign(dummy, {
      id: undefined,
    });
    return user;
  }
}
```

## Example: Adding a new port and its adapter

In a scenario where the application relies on a external 3rd-party service to implement a business rule, the port must be located at the **domain** layer, thus:

```txt
src/
└── {feature}/
    ├── domain/
    │   ├── ...
    │   └── services/
    │       ├── my-new-external.service.port.ts
    │       └── ...
    └── infrastructure/
        ├── services/
        │   ├── external-service-http-adapter/
        │   │   ├── my-new-external-service-http.service.ts
        │   │   └── external-service-http-adapter.module.ts
        │   └── ...
        └── {feature}-infrastructure.module.ts
```

The port must be defined as a `abstract class` because we will use the class as injection token as well.

The implementation of that port will be defined in the **infrastructure** layer of the feature or in the `shared` directory in case of services that can be used by multiple features.

At the 'infrastructure' module of the feature, we will bind the adapter as the implementation of the new port.

In such example, the final result would look like this:

```ts

  async foo() {
    // ...
  }
}
```

```ts

  providers: [MyNewExternalHttpAdapterService],
```

# Application

## Configuration

Configuration will follow the 12-Factor App methodology (https://12factor.net).

- **Environment Variables**: All dynamic configuration will be provided via environment variables. Not necessarily '.env' files, since we can have some variables injected via Shell.
- **Development Environment**: A `.env` file (added to .gitignore) will be used for local development. A `.env.example` file will be committed to the repository as a template.
- **Structure**: The `.env` file will be organized with commented sections (for example, # APP, # DATABASE). Variable names must be in SCREAMING_SNAKE_CASE (example: DATABASE_URL).
- **Loading**: Configuration will be loaded exclusively through the third-party library `zod`. Direct access to process.env in application code is prohibited.
- **Validation**: A zod schema will be used to validate all environment variables at application startup. The application must fail immediately if any required configuration is missing or invalid.
- **Test Override**: A `.env.test` file (added to .gitignore) can be used to override configurations during tests. Tests should be executed using dotenv-cli to load the `.env` first and then the `.env.test`, ensuring that test-specific values take priority.

To load '.env' files in the application, we will not use libs like `dotenv` as this implies a requirement from the application for '.env' files.  
Instead, we will use the Node.js CLI feature: `--env-file` for local development, `--env-file-if-exists` for running the application in production.

## Error Handling

All the non 2xx HTTP responses will be formated as defined by RFC 7807 Problem Details.  
To achieve that, the `CatchAllExceptionsForHttp` exception filter is globally applied.

All domain errors (ie, exceptions that inherits from `DomainError`) are mapped into 422 HTTP response by default.
All validation errors (ie, exceptions that inherits from `ValidationError`) are mapped into 400 HTTP response by default.

In order to change the default HTTP status, you must wrap the code in a try-catch block like this:

<details>

```ts
// some controller file (presentation layer)
@Controller("users")
class UserQueryController {
  async getUserInfo(
    @Param() paramsDto: GetUserInfoPathParamsDTO,
  ): Promise<UserInformationResponseDTO> {
    try {
      const result = await this.retrieveUserInformationsUseCase.execute({
        userEmailAddress: paramsDto.user_email,
      });

      return UserResponseMapper.fromDomain(result.user);
    } catch (err) {
      if (err instanceof UserNotFoundError) {
        // <- performing the mapping HERE
        throw new NotFoundException(err.message, {
          cause: err,
        });
      }
      throw err; // rethrowing for others errors
    }
  }
}
```

</details>

With that approach only the files at presentation layer are aware of the HTTP related exceptions.

## Events

| Type                           | Role                                                   | Where it is             |
| ------------------------------ | ------------------------------------------------------ | ----------------------- |
| **Domain Events**              | Something relevant _happened in the domain_            | `domain/events`         |
| **Application Events**         | Something relevant _for the application / integration_ | `application/events`    |
| **Integration / Infra Events** | Technical publication (Pub/Sub, Kafka, etc)            | `infrastructure/events` |

- Domain events: Represents facts in the domain; Are immutable; Don't know who consumes; Don't know how they will be published; Don't depend on infrastructure, libs or frameworks
- Application events: Represents something relevant for the application / integration; Are mutable; Know who consumes; Know how they will be published; Depend on infrastructure, libs or frameworks
- Integration / Infra events: Represents technical publication (Pub/Sub, Kafka, etc); Are mutable; Know who consumes; Know how they will be published; Depend on infrastructure, libs or frameworks

To understand how the events are emitted, follow this rule of thumb:  
Entities / Aggregates or Application Services create events. Application (use cases) decides when to publish. Infrastructure publishes the events.

## Database

We will use PostgreSQL.  
Use of the 3rd-party lib `pg` as PostgreSQL client for Node.js.  
Use of the 3rd-party lib `kysely` as a query builder to perform operations instead of using `pg` directly.

### Tracking schema changes

Database changes will be orchestrated via migrations generated and executed with the help of the CLI tool [`dbmate`](https://github.com/amacneil/dbmate).

### Database models

Tables are declared as TypeScript interfaces using the `Row` suffix convention. Each `*.db.ts` file exports an interface that maps 1:1 to the database table columns. Example for a 'user' entity:

```ts
// file infrastructure/persistence/schemas/user.db.ts
export interface UserRow {
  id: string;
  email_address: string;
  current_work_center_id: string | null;
  created_at: Date;
  updated_at: Date;
}
```

Rules:

- file in format `infrastructure/persistence/schemas/{entity}.db.ts`
- Interface names use PascalCase with `Row` suffix (e.g., `PmaCaseRow`, `PmaUserRow`)
- Column names in the interface match the DB column names exactly (snake_case)
- Use `| null` for nullable columns
- Import domain value-object types when columns map to enums (e.g., `status: PmaCaseStatus`)
- Never import DB models in the 'domain' folder

### Error handling for persistence layer

Repositories will not throw exceptions on SELECT queries that do not return rows. Instead, they will return null for single-row queries or an empty array for multi-row queries.
Database-specific errors (for example, unique constraint violations) will be caught within the repository adapter and rethrown as custom domain exceptions, but without losing the original exception.

## Server API's Input and Output Serialization

We use a NestJS built-in middleware to ensure that JS objects are serialized into JSON texts for responses.

We use the ExpressJS middleware for parsing incoming `"application/json"` HTTP payloads into JS objects at `JsonBodyParserMiddleware` that will be available when using the `@Body()` decorator; in there you can find the limit allowed for the payload.

For input validation

We **do not** perform any output validation for HTTP responses as the 'response mapper classes' used in controllers classes are type-safe and should be enough to ensure that the response schema is being satisfied.

## Automated Testing

### Unit tests

Unit tests focus on a single "unit" of code. To achieve this, external dependencies are often replaced with "test doubles" such as mocks, stubs, or spies.

To run all the unit tests, execute, inside the `apps/backend` folder: `pnpm unit/test`

When writting such tests, **you must**:

- ✅ all the test suite files close the the subject under test (SUT). For example: if the file is `mappers/user-response.mapper.ts` then its unit test suite must be `mappers/user-response.mapper.spec.ts`
- ✅ if the SUT is a class called `MyService`, use the `describe("MyService", ...)` and `it("#myMethod()")` conventions, to easily identify the components under test
  And **do not**:
- ❌ spawn a real web server
- ❌ have multiple SUTs in the same test suite file
- ❌ have unit tests for `controllers` (**presentation** layer) as they must be tested at E2E stage
- ❌ have unit tests for `repositories` (**infrastructure** layer) as they are useless unless we have a real database connection in place
- ❌ tests that are very volatile, ie., that are testing the implementation instead of the behavior

### Integration tests

Integration focuses on verifying that different modules, components, or services within an application interact correctly and function as a cohesive unit.

useful when testing use cases (**application** layer) that rely on various external dependencies so that you could control their behavior.

To run all the integration tests, execute, inside the `apps/backend` folder: `pnpm integration/test`

When writting such tests, **you must**:

- ✅ all the test suite files under the `backend/test/integration/` directory, mirroring the file structure defined at `backend/src/` directory; with the suffix `.spec.ts`
- ✅ all the modules must have a equivalent test suite only to ensure that they don't have a 'dependency error'. Note that for this we will ignore the `DatabaseModule` by replacing it with a No-op module because we can't rely on a real database connection
  And **do not**:
- ❌ spawn a real web server
- ❌ relies on a real database connection
- ❌ have integration tests for `controllers` (**presentation** layer) as they must be tested at E2E stage
- ❌ have unit tests for `repositories` (**infrastructure** layer) as they are useless unless we have a real database connection in place
- ❌ tests that are very volatile, ie., that are testing the implementation instead of the behavior

### E2E tests

End-To-End testing is a software testing method that validates entire software from starting to end along with its integration with external interfaces.  
**But** in the context of this app - where a single web server REST-like API will be expose for Backend applications, the E2E will be written for:

- ensure that the database connection is established - by testing the endpoints exposed by the module `HealthModule`
- ensure that external dependencies (used through ports) are invoked as expected depending
  - using mocks for external dependencies
  - not using the real external dependency, as we will only test their API contract
- ensure that critical behavior that rely on responses from external dependencies (used through ports) will work as expect
  - using mocks for external dependencies
- ensure that all endpoints that should be private are actually private—that is, they return 403 Forbidden when an invalid Bearer token is provided
- ensure that all controllers (implemented in `/presentation/`) have test coverage
- ensure that database changes occur as expected when each endpoint is correctly called
- ensure that all features (implemented in `/application/use-cases/`) have test coverage

To run all the unit tests, execute, inside the `apps/backend` folder: `pnpm e2e/test`

When writting such tests, **you must**:

- ✅ respect the following file naming conventions:
  - for a controller class name `FooController` there should be a directory called `{feature}/presentation/foo-controller`
  - for each method in the controller class `FooController` there should be a dedicated file called `{feature}/presentation/foo-controller/{method-name}.e2e-spec.ts`
- ✅ all the test suite files under the `backend/test/e2e/` directory, mirroring the file structure defined at `backend/src/` directory; with the suffix `.e2e-spec.ts`
- ✅ use the `supertest` lib to simulate HTTP requests so that we don't need to initiate a real server
- ✅ follow the BDD approach by using the `describe()` to define the feature under test and to the scenario being evaluated; use `it()`/`test()` to implement the expectation
- ✅ organize tests with nested `describe()` blocks: outer for the endpoint/feature, inner for scenarios like "When the given input is valid"
- ✅ use `beforeAll` to bootstrap the NestJS app using the `createAppModuleForE2ETest()` utility
- ✅ use `afterAll` to close the app gracefully with try-catch to prevent test failures during cleanup
- ✅ obtain the database connection via `getDatabaseClient().connection` and the HTTP server via `app.getHttpServer()`
- ✅ use `request(underlyingHttpServer)` from `supertest` to make HTTP requests (never use `fetch` or `axios`)
- ✅ use raw SQL queries via `sql` tagged template from `kysely` (e.g., `db.execute(sql`...`)`) for database setup, verification, and cleanup
- ✅ organize test code with `#region` comments: `[db-setup]`, `[db-cleanup]`, `[db-checking]`, `[external-services-setup]` for better readability
- ✅ follow the AAA pattern (Arrange-Act-Assert) with clear separation using comments or blank lines
- ✅ always verify BOTH `statusCode` AND `type` (content-type) in assertions, not just the status code
- ✅ use `expect.soft()` for multiple assertions to see all failures, not just the first one
- ✅ test both success and error scenarios for each endpoint (e.g., 200 OK, 404 Not Found, 400 Bad Request)
- ✅ use TypeScript types for DTOs in test arrangements (e.g., `const bodyDto: RegisterNewUserDTO = { ... }`)
- ✅ use factories from `test/e2e/common/factories/` to generate test data (e.g., `makeNewUser()`, `resolveRandomEmailAddress()`)
- ✅ ensure database isolation by cleaning up test data in `[db-setup]` before the test and in `[db-cleanup]` after assertions
- ✅ verify database state changes using `[db-checking]` region after operations that modify data
- ✅ mock external services by getting them via `app.get<DeepMockProxy<Port>>(Port)` and configuring mock behavior
- ✅ use descriptive test names that explain the scenario and expected outcome (e.g., "and there is no user with the given email address, it should reply with a 404 status code...")
- ✅ when testing error responses, verify the exact structure of the Problem Details JSON (type, title, status, detail)
- ✅ declare variables at suite level (`let app`, `let db`, `let underlyingHttpServer`) and initialize them in `beforeAll`

And **do not**:

- ❌ spawn a real web server (use `app.getHttpServer()` with supertest instead)
- ❌ validate input payloads schemas (query, path parameters, body) — this should be tested in integration tests
- ❌ interact with real external services (always mock ports/adapters for external dependencies)
- ❌ use `fetch()` or `axios` for HTTP requests (use `supertest` exclusively)
- ❌ leave database test data behind after tests complete (always clean up in `[db-cleanup]` regions)
- ❌ share mutable state between tests without proper isolation
- ❌ use hardcoded IDs or emails (use factories to generate random test data)
- ❌ test multiple endpoints in a single test case (one endpoint behavior per test)
- ❌ skip checking the response content-type header (always verify both status and type)
- ❌ use `expect().toBe()` for object comparisons (use `toEqual()` or `toStrictEqual()` instead)
- ❌ forget to type your DTOs and response bodies in assertions
- ❌ make assumptions about database state (always set up the exact state you need in `[db-setup]`)
- ❌ use `app.listen()` or start a real HTTP server (the app is initialized but not listening)
- ❌ test implementation details of services or repositories (focus on HTTP contract and database effects)
- ❌ ignore cleanup in `afterAll` even if it might fail (wrap in try-catch to prevent cascading failures)

#### E2E Test Structure Pattern

Here's a complete example showing the expected structure and patterns for E2E tests:

```typescript
// ..
describe("Feature description - HTTP_METHOD /api/path", () => {
  let app: NestExpressApplication;
  let db: DatabaseClient["connection"];
  let underlyingHttpServer: Server;

  beforeAll(async () => {
    const { appFixture, getDatabaseClient } = await createAppModuleForE2ETest();

    app = appFixture;
    await app.init();

    db = getDatabaseClient().connection;
    underlyingHttpServer = app.getHttpServer();
  });

  afterAll(async () => {
    try {
      await app.close();
    } catch {
      // do nothing
    }
  });

  describe("When the given input is valid", () => {
    test("and [specific scenario], it should [expected behavior with status code]", async () => {
      // Arrange
      const requestData: RequestDTO = {
        field: "value",
      };

      // #region [db-setup] ensuring database state for this test
      await db.execute(sql`DELETE FROM "table" WHERE "field" = ${requestData.field}`);
      await db.execute(sql`INSERT INTO "table" ("field") VALUES (${requestData.field})`);
      // #endregion

      // #region [external-services-setup]
      const externalService = app.get<DeepMockProxy<ExternalServicePort>>(ExternalServicePort);
      externalService.someMethod.mockResolvedValue("mocked result");
      // #endregion

      // Act
      const res = await request(underlyingHttpServer)
        .post("/api/path")
        .send(requestData)
        .set("Content-Type", "application/json");

      // Assert
      expect.soft(res.statusCode).toBe(HttpStatus.CREATED);
      expect.soft(res.type).toBe("application/json");
      expect.soft(res.body).toStrictEqual<ResponseDTO>({
        id: expect.any(String),
        field: requestData.field,
        createdAt: expect.any(String),
      });

      // #region [db-checking] verify database changes
      const dbResult = await db.execute(
        sql`SELECT * FROM "table" WHERE "field" = ${requestData.field}`,
      );
      expect.soft(dbResult.rows).toHaveLength(1);
      expect.soft(dbResult.rows[0]["field"]).toEqual(requestData.field);
      // #endregion

      // #region [db-cleanup]
      await db.execute(sql`DELETE FROM "table" WHERE "field" = ${requestData.field}`);
      // #endregion
    });

    test("and [error scenario], it should reply with [error status] and problem details", async () => {
      // Arrange
      const invalidData: RequestDTO = {
        field: "invalid-value",
      };

      // #region [db-setup] ensure the condition that causes the error
      await db.execute(sql`DELETE FROM "table" WHERE "field" = ${invalidData.field}`);
      // #endregion

      // Act
      const res = await request(underlyingHttpServer).get(`/api/path/${invalidData.field}`);

      // Assert
      expect(res.statusCode).toBe(HttpStatus.NOT_FOUND);
      expect(res.type).toBe("application/problem+json");
      expect(res.body).toEqual({
        type: "ResourceNotFoundError",
        title: "ResourceNotFoundError",
        status: 404,
        detail: `Resource with field "${invalidData.field}" was not found`,
      });
    });
  });
});
```

Key patterns demonstrated:

- Suite-level variables with proper types
- `beforeAll`/`afterAll` lifecycle hooks to control app's lifecycle
- Nested `describe()` for scenarios
- `// #region` comments for code organization
- AAA pattern (Arrange-Act-Assert)
- `expect.soft(...)` for multiple assertions in a test that will run a cleanup even on failures
- Both success and error case testing; but avoiding dummy tests such as DTO input validation
- Database setup, verification, and cleanup
- External service mocking
- Type-safe DTOs in assertions

### Overview on what to test

The following glob patterns are for files that generally should have an **unit test**:

- `**/presentation/**/*.guard.ts`
- `**/presentation/middlewares/*.filter.ts`
- `**/domain/entities/**.entity.ts`
- `**/utils/*.util.ts`

The following glob patterns are for files that generally should have a **integration test**:

- `**/*.module.ts` - except the `database.module.ts` (`DatabaseModule`)
- `**/shared/infrastructure/**`
- `**/domain/services/**` - not including real interactions with database (`DatabaseModule`)
- `**/application/services/**` - not including real interactions with database (`DatabaseModule`)

The following glob patterns are for files that generally should have a **E2E test**:

- `**/presentation/controllers/**`
- `**/middlewares/**`

There are code componets that **do not** require any sort of automated tests and may not even require test coverage because they don't hold any business logic nor anything else worth to test; namely:

- utilities at the `test/**/*` directory
- files with the suffix `.port.ts`
- files for the glob pattern `/presentation/mappers/**/*.mapper.ts`
- files for the glob pattern `/presentation/middlewares/**/*.middlewares.ts` that just use some 3rd-party lib
- the file `/shared/infrastructure/environment.configuration.ts`
- the directory `/shared/infrastructure/logger`
- the directory `/shared/infrastructure/telemetry`
- the file `/shared/infrastructure/logger/logger.module.ts`

When the coverage is not needed, the file will have a `/* v8 ignore file */` in their first line to indicate that.

## API Documentation

We are following a code-first approach to generate OpenAPI v3 specification of the web server's APIs.

To do that, we must use the `@Api*()` decorator factories. For example:

```ts
// ... some controller file
  @Get(":user_email")
  @ApiOperation({ summary: "Get informations about a given user" })
  @ApiOkResponse({ type: UserInformationResponseDTO })
  @ApiExtraModels(UserNotFoundErrorResponseDTO)
  @ApiNotFoundResponse({
    content: {
      "application/problem+json": {
        schema: {
          $ref: getSchemaPath(UserNotFoundErrorResponseDTO),
        },
      },
    },
  })
  async getUserInfo(
    @Param() paramsDto: GetUserInfoPathParamsDTO,
  ): Promise<UserInformationResponseDTO> {
    ...
  }
```

Since the error handling (ie, when the API reply with a status code other than 2xx) enforces the usage of the Problem Details RFC 7807, when registering error response we must write the `"application/problem+json"` just because the default is always `"application/json"`.

When running the application, a Swagger UI page will be available at `/openapi` route;  
while the JSON version of the OpenAPI specification is available at `/openapi.json` page and the YAML version will be available at `/openapi.yaml`
